# Domain glossary

The product is conceived in French and written in English. Each concept has
exactly one English identifier: use it, do not coin a synonym. A new concept
gets its row here in the same commit that introduces it. The rules that go
with these names (revisions, audit block, derived state, ordering) are in
`CLAUDE.md` section 4.3.

| French | Identifier |
| --- | --- |
| texte source | `SourceText` |
| version du texte source | `SourceTextVersion` — append-only, `versionNumber` from 1, and the current one is the highest. Editing appends; nothing overwrites a version and nothing deletes one, which is what lets a later stage be traced to the text it was produced from (CAL-046) |
| étape en aval | `DownstreamStage` = `analysis` / `direction` / `bible` / `outline` / `chapters`, in that order — the chain a source-text edit runs down. The array order **is** the dependency graph; there is no second table naming upstreams |
| obsolescence potentielle | `SourceTextObsolescence` in `@calepin/shared/obsolescence` — **derived, never stored**. A stage is in doubt when it exists and was either produced before the current version or built on a stage that is. Provenance, never quality: it names what to look at and **never deletes or regenerates anything**. The analysis is judged exactly, through `AnalysisSectionRevision.sourceTextVersionId`; the four stages below it by whether their own row has moved since |
| propagation de l'obsolescence | `assessStageChain` in `@calepin/shared/obsolescence` (CAL-046, extracted by CAL-086) — the walk itself, once: down the chain from the change, a stage is in doubt when it exists and was either hit directly or descends from something that was, and doubt never travels backwards. What a caller parameterises is the **direct reason** and nothing else, so two changes cannot end up with two inheritance rules. Inheritance is the load-bearing half: without it, rebuilding one stage would report a clean project while everything below still descends from what was replaced |
| analyse, diagnostic narratif | `Analysis` |
| fait explicite / interprétation | `AnalysisElement.kind` = `FACTUAL` / `INTERPRETATION` — the marker every element of the diagnostic carries, mirrored by `ANALYSIS_ELEMENT_KINDS`. Asked for by the prompt, carried by the schema, and **enforced after the fact** by `verifyAnalysisEvidence` below: a claim the text does not support is not left to the model's goodwill (CAL-071) |
| citation d'appui | `AnalysisElement.evidence` — the passage of the source text an element rests on, verbatim and continuous, or null. A `FACTUAL` element owes one; an `INTERPRETATION` may cite the passage it starts from. Never elided, never translated, never corrected: the prompt forbids the hole rather than the check parsing it, because stitching fragments back together is how a quotation nobody wrote comes to be believed |
| citation vérifiée | `createVerbatimMatcher` in `@calepin/shared/text` — the comparison every _cite what supports it_ rule ends in, over **words rather than characters**: typography is what a model retypes wrong (guillemets, the apostrophe, the non-breaking space, an em dash typed as a hyphen) and a word is what a paraphrase changes. Accents stay significant, a match lands on word boundaries, and the text is reduced once per matcher rather than once per quotation. Shared rather than domain-owned for `countWords`'s reason: CAL-089 asks it of a chapter and CAL-101 of a revision, and a domain may not import a domain |
| reclassement d'un élément non appuyé | `verifyAnalysisEvidence` in `@calepin/analysis` (CAL-071) — reads every quotation back against the source text: an element marked `FACTUAL` that cites nothing, or whose quotation is not in the text, comes back `INTERPRETATION`, and a quotation that is not there is dropped whatever the marker, because CAL-072 puts it on screen. **Provenance, never sufficiency** — it answers whether the passage exists, never whether it supports the statement. Only the marker the model _chose_ is rewritten: `ANALYSIS_FIXED_KINDS` names the five sections whose marker their own definition decides, which is also what keeps the answer inside the schema that produced it. Its result is branded (`VerifiedSourceTextAnalysis`, minted only here and never serialised), so persistence takes a checked analysis instead of remembering to check one; its report is counts, sections and positions, never a word of the text (§9) |
| diagnostic en dix-sept sections | `sourceTextAnalysisSchema` in `@calepin/analysis` — the answer to `analyze-source-text`, shaped exactly as CAL-014 stores it: one camelCase field per `AnalysisSection` (`ANALYSIS_SECTION_FIELDS`, pinned total and onto), each element carrying `kind`, `statement`, a nullable verbatim `evidence` and — in the eleven listed sections — a `label`. `kind` is a **literal** where the section's definition decides it (the factual summary is `FACTUAL`; preserve, weaknesses, cliché risks and potential are `INTERPRETATION`), a section may be empty only where absence is meaningful, and the word targets (`ANALYSIS_WORD_TARGETS`) travel into the prompt as variables while bounding the schema — the CAL-055 discipline (CAL-070) |
| détection des risques de clichés | `detect-cliche-risks` (CAL-075) — the dedicated pass over the déjà-lu, separate from the diagnostic's `CLICHE_RISKS` section for §5.4's reason: four fronts (`CLICHE_RISK_CATEGORIES` = `situation` / `character` / `formula` / `reversal`), and per finding a **required** verbatim passage, why it is conventional and what it forecloses (`clicheRiskDetectionSchema` in `@calepin/analysis`, at most twelve findings). **No score, structurally**: the specification (1195–1199) forbids a banality or originality number, so the contract carries no numeric field anywhere and a test pins it — what argues is `whyConventional` and `whatItPrevents`, in words. `verifyClicheRiskEvidence` reads every quotation back through `createVerbatimMatcher` and **drops whole** a finding whose passage is not in the text (evidence is required, so there is no demotion to fall back to); its result is branded (`VerifiedClicheRiskDetection`), its report counts and categories only (§9). Writes into the analysis (`MISSION_WRITE_TARGET_KIND` = `analysis`), so it excludes `ANALYZE_SOURCE_TEXT` running concurrently |
| évaluation du potentiel romanesque | `assess-novel-potential` (CAL-076) — the argued answer to _ce que le texte peut soutenir sur la longueur cible_, read off the **validated** analysis and the source text. Four axes plus a synthesis (`novelPotentialAssessmentSchema` in `@calepin/analysis`): `expansions` (**at least three** — the backlog's floor as the array's own minimum), `exhaustions`, `gaps` (absences, so they carry no evidence field) and `fragilities` (**at least two**), under `overall`. **No score, structurally**, as CAL-075: no numeric field anywhere, pinned by test — the minimums demand a prioritisation, never an invention, and the appraisal says how far each element carries. `evidence` is **nullable** (an appraisal is an interpretation; its standing is its argument), so `verifyNovelPotentialEvidence` **clears** an unfound quotation to null instead of dropping the appraisal — a drop could break the minimums; result branded (`VerifiedNovelPotentialAssessment`), report counts and `{ list, index }` positions only (§9). The target length arrives as a prompt variable resolved from the project (`resolveNovelTargetWordCount`). Writes into the analysis, so it excludes the diagnostic and the cliché pass running concurrently |
| traçabilité d'un élément | `@calepin/shared/provenance` (CAL-073) — the pattern the specification's principle 4.2 asks for, established on the analysis and **written to be reused as is by the bible, the outline and the chapters**. Three rules: an element has an identity that outlives the revision holding it (`lineageId`), its origin is monotone under editing (`originAfterEdit`), and being validated is derived rather than stored (`resolveProvenanceState`). In `shared` rather than in a domain for `createVerbatimMatcher`'s reason — four epics need the same answer and a domain may not import a domain |
| origine d'un contenu | `ContentOrigin` = `GENERATED` / `EDITED` / `USER_WRITTEN` — who authored the wording that is there **now**, and the only thing a row stores. Monotone: a human edit turns `GENERATED` into `EDITED` and never back, `USER_WRITTEN` never becomes `EDITED`, and only a generation writes `GENERATED` again — with new content. That monotonicity _is_ _l'origine reste lisible après édition_, expressed as a total function instead of a habit. Three members for `DirectionOrigin`'s reason; no `VALIDATED` member, because being validated is not an authorship |
| lignée d'un élément | `lineageId` — the identity of one element across the revisions of its container, minted when it first appears and copied by every later revision that keeps it. Every container the pattern applies to is append-only, so an edit writes _new_ rows: a row is the wrong place to hang an identity that has to outlive it. It is what carries the origin forward, and what gives an annotation something to point at that a rewrite of the section does not destroy — which is why `AnalysisAnnotation` names `(analysisId, lineageId)` and no longer an element row. Unique within a revision (`@@unique([sectionRevisionId, lineageId])`), never a primary key: two revisions legitimately hold the same lineage |
| état de traçabilité | `ProvenanceState` = `proposed` / `accepted` / `edited` / `user-written` — **derived, never stored**, from the element's origin and the origin of the revision holding it. An element still `GENERATED` inside a revision a person authored is one they read and kept: _validé_. A column beside the two that already answer this would be a second answer able to disagree with them, the reason `AnalysisSectionRevision` carries no `isCurrent` and `Project.status` is recomputed. The four French labels are `apps/web`'s (`lib/analysis-edit.ts`), the division `project-action-error.ts` already draws |
| édition d'une section d'analyse | `editAnalysisSection` in `@calepin/shared/repository` — appends a revision, `origin: EDITED`, carrying every element's provenance across it by lineage; the sixteen other sections and their notes are untouched by the statement. An identical submit writes nothing (`carryProvenance`'s `unchanged`), a validated analysis is refused (`CONFLICT`), and the revision records the **current** source text version rather than the previous revision's — the column means _the version this revision was produced against_, so editing a section takes it out of `SourceTextObsolescence`'s doubt, which is the author's call and nobody else's. What a section may say is the domain's (`parseAnalysisSectionEdit` in `@calepin/analysis`, derived from `sourceTextAnalysisSchema.shape` so the manual and generated write paths share one schema) and is applied by the caller, since `shared` may not import a domain (§3.2) |
| régénération ciblée d'une section | `regenerate-analysis-section` (CAL-077) — la relance d'**une** section, avec la consigne complémentaire facultative de l'auteur. `editAnalysisSection`'s twin in `@calepin/shared/repository` (`regenerateAnalysisSection`), and every difference is the point: `origin: GENERATED`, the revision names its `Generation` (ADR-001's link), **no lineage is carried** — §6 forbids trusting a model with an identifier and matching by position would move a note about one theme onto another — and there is no identical-answer short circuit, because an answer that happens to match is still one somebody paid for. The acceptance criterion is an absence and is proved as one: `analysis-regeneration.integration.test.ts` photographs every row of every analysis table and compares the whole photograph, so a column nobody anticipated fails there too. Writes into the analysis (`MISSION_WRITE_TARGET_KIND` = `analysis`), so it excludes the diagnostic, the cliché pass and the potential assessment running concurrently |
| consigne complémentaire | `analysisSectionRegenerationInputSchema.instruction` in `@calepin/analysis` — the author's word about what to do differently, required-but-nullable so a composer decides rather than forgets, bounded by `ANALYSIS_REGENERATION_INSTRUCTION_CHAR_CEILING`, and read by `parseAnalysisRegenerationInstruction` (absent, empty and blank are one answer). It is part of the **ask**, not of the prompt only: the schema is what `Generation.input` stores and `generationIdempotencyKey` digests, so asking again with a different consigne is a different generation while a redelivered job is the same one. The prompt gives it authority over the _angle_ of the section and never over the source text — a consigne cannot manufacture what the text does not carry, which is why the column is a digest and never a rendering (§9) |
| notes orphelines | `AnalysisSectionRegeneration.orphanedAnnotationCount` — how many of the author's notes stopped bearing on what is now on screen. Not a deletion count and not a side effect: the rows are never addressed by the statement, and `getAnalysis` has always shown only the notes whose lineage is in the current revision. Reported because nothing can recompute it afterwards without re-reading the revision that was replaced, and a count, so it is safe to log (§9) |
| annotation libre | `AnalysisAnnotation` — a note the author attaches to one element, by lineage. Mutable, so it carries the audit block; bounded by `ANALYSIS_ANNOTATION_CHAR_CEILING`; and resolved against the analysis before it is written, because no foreign key can check a lineage and that is the price of a note that survives the rewrite it comments on |
| direction romanesque | `Direction`; the chosen one is the `canonicalDirection` |
| trois directions proposées | `directionProposalsSchema` in `@calepin/direction` (CAL-079) — the answer to `propose-directions`: exactly `DIRECTION_PROPOSAL_COUNT` directions, each carrying the specification's twelve attributes under the `CreativeDirection` columns' own spellings **plus** `dimensionTreatments`, the declaration the `direction` stage rule already orders — one treatment per `SOURCE_DIMENSIONS` entry, total by construction. Ahead of the row exactly as `novelPotentialAssessmentSchema` is ahead of any row storing it: the column belongs to the persistence task. **No score, structurally**, as CAL-075/076 — no numeric field anywhere, pinned by test; the twelfth attribute argues in words. Word targets and list bounds (`DIRECTION_WORD_TARGETS`, `DIRECTION_LIST_COUNTS`, minimums as prioritisation demands, `charactersToIntroduce` alone may be empty) bound the schema and travel into the prompt as variables — the CAL-055 discipline, with `dimensionKeys` composed from `SOURCE_DIMENSIONS` + `SOURCE_DIMENSION_LABELS` so the keys are never restated in prose. **Compliance is a report, never a rewrite**: `checkDirectionProposalCompliance` maps the declaration into `checkFreedomCompliance`, and an over-ceiling declaration has no mechanical repair — the caller decides, the re-ask is the executor task's. The prompt makes the constraints outrank divergence and names where divergence lives when a dimension is locked; the engine declaration and its gate are their own entries below (CAL-080) |
| moteur narratif d'une direction | `NarrativeEngine` in `@calepin/direction` (CAL-080) — what a direction declares on five closed axes: `conflictNature`, `tensionSource`, `protagonistStake`, `shiftTrigger`, `resolutionNature` (`NARRATIVE_ENGINE_AXES`, order pinned). Every member names a dramatic mechanism and none can name a place, an era, a milieu or a cast — which is what turns _ne différer que par le décor_ into a comparison of two five-tuples. Declared exactly as `dimensionTreatments` is: describing the direction as it is, part of `directionProposalsSchema`, compared mechanically afterwards. The French copy lives beside the vocabulary (`NARRATIVE_ENGINE_COPY`) for `FreedomConstraint`'s reason — the author reads the same clauses the prompt quotes (`describeNarrativeEngineAxes`, `describeNarrativeEngine`) |
| divergence des moteurs narratifs | `checkDirectionDivergence` in `@calepin/direction` (CAL-080) — the gate the CAL-079 prompt only worded: two engines differing on fewer than `NARRATIVE_ENGINE_DIVERGENCE_MINIMUM` (2) of the five axes are **one** engine, whatever the décor. Two, held from both sides: one differing axis is the same mechanism with a variant outcome — and the cheapest evasion — while the freedom policy pins engine axes at `LOW`, leaving only tension source and trigger guaranteed free, so a higher demand would teach the model to lie in its declaration. A report, never a `Result` (`checkFreedomCompliance`'s doctrine): the pairs with shared and differing axes, `retained` (prefix-greedy, first listed wins) and `regenerate` — the targeted relaunch's complete input, which prompt V3's `excludedEngines` variable is ready to quote; _executing_ the re-ask is the executor task's, exactly as CAL-079 recorded for the compliance re-ask. Indexes and axis identifiers only, safe to log (§9) |
| évaluation critique d'une direction | `evaluate-direction` (CAL-081) — the outside reading of **one** direction, strictly separate from the mission that proposes them (principle 6.2): the direction's own `novelPotentialAssessment` argues _for_ it, this mission argues _about_ it. Four argued lists and nothing else (`directionEvaluationSchema` in `@calepin/direction`): `promises` (min 2), `shortfalls` (min 2), `conventions` (min 1 — _rien de convenu_ would flatter the sibling mission's output; a dominant genre always carries a most-conventional element to name) and `comparativeWeaknesses` (min 1 — the argued case for _peut être moins intéressante que les autres_, the siblings entering the prompt as composed context and never the schema as an index a model would choose). **No score, structurally** as CAL-075/076/079, and **no synthesis field** — a free synthesis is the one place a global verdict could live unattached to any element. _Rattachée à un élément précis_, held twice: every item names in `element` the proposal field it bears on (`DIRECTION_ELEMENTS`, pinned against `directionProposalsSchema`'s own keys) and may cite in `evidence` (nullable) a verbatim passage — verified by `verifyDirectionEvaluationEvidence` against **two corpora**, the source text and the direction's own prose field by field, an unfound quotation cleared to null (CAL-076's regime; the declarations are targeted by `element` and argued in words, never quoted). Result branded (`VerifiedDirectionEvaluation`), report counts and `{ list, index }` only (§9). Writes into one `direction` target, so two directions may be evaluated concurrently |
| direction écartée | `CreativeDirection.discardedAt` (CAL-083) — when the author wrote a proposal off, `discardReason` beside it for why, or null when they gave none. A **timestamp, never a status**, `Project.archivedAt`'s shape: a status column would be a second answer able to contradict `origin` and `isCanonical`. Nothing is deleted and nothing is blanked — the backlog requires a discarded direction to stay consultable, so the row survives whole and `getDirectionsForComparison` keeps returning it; the caller splits the array, because filtering in the repository would make _disparue_ and _écartée_ one answer. Written by `discardDirection` in `@calepin/shared/repository`: one statement, `NOT_FOUND` for a row that is not there or not theirs, `CONFLICT` for one already écartée (look again, do not write again) and for the canonical one (writing off the direction the novel is built on is a change of mind about the novel, and goes through whatever un-chooses it). No `discardedById`: the audit block already names who last wrote the row. The reason is the author's own prose (§9) — stored, shown back, quoted to the model that writes the replacement, never logged |
| remplacement d'une direction | `replace-direction` (CAL-083) — **one** direction proposed in place of one written off, never three. Its own mission rather than `propose-directions` re-rendered with a count of one, the case §5.4 and CAL-077 already settled: the answer is one direction, the constraint is three engines it may not reproduce, and the ask carries the author's reason. `directionReplacementSchema` in `@calepin/direction` reuses `directionProposalSchema` rather than restating it, so a replacement is a peer of the three it joins; `directionReplacementInputSchema` is what `Generation.input` stores — the source text version, the discarded direction, the reason and the excluded engines, which are the ask itself and not a derivation of it, so a kept direction reworded without its engine moving is genuinely the same question. Writes into `directions` (`MISSION_WRITE_TARGET_KIND`), which excludes a concurrent `propose-directions` **and** a second concurrent replacement — two of them would each be told to avoid the engines the other is about to create |
| exclusion d'un moteur narratif | `checkDirectionReplacement` in `@calepin/direction` (CAL-083) — the backlog's acceptance criterion as a function: a replacement differing from any excluded engine on fewer than `NARRATIVE_ENGINE_DIVERGENCE_MINIMUM` axes **is** that engine, whatever the décor. Built on `compareNarrativeEngines`, never a second rule. The exclusion set is `excludedEnginesForReplacement`: the discarded direction's engine first — index `0` is _the one that was rejected_, the only distinction a report or a log line can draw between three otherwise interchangeable clauses — then the kept ones', because a replacement colliding with a direction still on screen would leave the author with two proposals and three cards. A **report, never a `Result`** (`checkDirectionDivergence`'s doctrine): the caller decides whether to re-ask, and the re-ask is the executor task's. No brand — the writer is in `@calepin/shared`, which could never read one (CAL-077's arrangement). Indexes, axis identifiers and booleans only, safe to log (§9) |
| combinaison d'éléments de plusieurs directions | `combine-directions` (CAL-084) — elements selected from two or three directions, one merged direction back **or** the explicit answer that the combination is irreducible, naming what excludes what. `directionCombinationSchema` in `@calepin/direction`: one strict object discriminated by `outcome`, its two branches (`direction`, `conflicts`) required-but-nullable and tied by a check — a root union's JSON Schema is a `oneOf` the structured-outputs subset refuses, and a null said is CAL-077's discipline: an absence written, never elided. The merged direction reuses `directionProposalSchema`, a peer of the proposals it draws from. An answer names a source direction by `DIRECTION_COMBINATION_SLOTS` (`first` / `second` / `third`) — a closed vocabulary, never a number (no score, structurally) and never an id (§6) — and every named `(slot, element)` pair is verified against the ask's own selection; an unverifiable one refuses the answer whole, because a conflict's anchor is its substance and there is no nullable to clear. The selectable elements are `DIRECTION_COMBINABLE_ELEMENTS` — the proposal's material, never its three self-descriptions (`novelPotentialAssessment`, `mainRisks`, `dimensionTreatments`), which the fusion writes for itself; `narrativeEngine` selected means _this engine dominates_. `checkDirectionCombinationSelection` runs **before** any generation (principle 6.5): `narrativeEngine` selected from two directions whose engines are distinct is the acceptance criterion's own case — _combiner deux moteurs incompatibles_ — reported with the pairs and their differing axes, no model needed. The ask is canonical (unique directions, unique elements per direction), so one ask digests once (CAL-058). Writes into `directions` (`MISSION_WRITE_TARGET_KIND`), excluding a concurrent proposal, replacement or second combination |
| moteur dominant | `checkDirectionCombinationAnswer` in `@calepin/direction` (CAL-084) — _un moteur dominant plutôt qu'un compromis mou_ as arithmetic on `compareNarrativeEngines`, never a second rule: a source engine **dominates** when the merged declaration differs from it on fewer than `NARRATIVE_ENGINE_DIVERGENCE_MINIMUM` axes — _is_ that engine, per the established equivalence. No engine selected: acceptable means **exactly one** dominant — zero is a foreign engine nobody asked for, two is the soft compromise, which is mechanically a candidate splitting the exactly-two axes two distinct sources differ on. Engine selected: dominated by a selected slot and distinct from every unselected one — which also holds for the degenerate admissible ask of two selected engines that are one engine. Presumes pairwise-distinct sources (the product's own proposals are divergence-gated) and degrades to refusal, never to acceptance. A report, never a `Result`; slots, axis identifiers and booleans only, safe to log (§9) |
| édition manuelle d'une direction | `editDirection` in `@calepin/shared/repository` (CAL-085) — reusing CAL-073's traceability pattern rather than its code: `directionContentSchema` in `@calepin/direction` is the same field schemas `directionProposalSchema` declares, minus `dimensionTreatments` (never persisted for any direction, generated or hand-written), the "one schema, two write paths" `parseAnalysisSectionEdit` already established one epic earlier. Origin moves `PROPOSED`/`EDITED` → `EDITED`, `USER_WRITTEN` stays `USER_WRITTEN` — a small restatement of `originAfterEdit`'s rule 2, typed on `DirectionOrigin` rather than imported from `@calepin/shared/provenance`, because that enum predates and diverges from `ContentOrigin` (`PROPOSED` vs. `GENERATED`) the way `ChapterRevisionOrigin` and `TargetLength` already restate their own literal unions (CAL-043). An identical resubmission writes nothing and leaves the origin untouched — compared field by field, the narrative engine by sorted entries rather than raw `JSON.stringify`, since PostgreSQL's `jsonb` does not promise to preserve key order. A discarded direction refuses `CONFLICT` (CAL-083's no-un-discard doctrine, extended); the canonical one may be edited — only _discarding_ it is blocked |
| direction canonique | `CreativeDirection.isCanonical` — the one direction the novel is built on, **one per project**, held by `creative_directions_canonical_per_project_key`, a partial unique index. Chosen by `selectCanonicalDirection` in `@calepin/shared/repository` (CAL-086): two updates — clear whichever row held it, set the named one — inside `withProjectStatus`, so the flag and the status the flag _is the evidence for_ move in one transaction and cannot disagree (`deriveProjectStatus` reads it for `BIBLE_TO_VALIDATE`). Nothing is un-chosen and nothing is deleted: the direction it replaces stays standing, readable and un-discarded, because replacing is not writing off. Four refusals, each with its own remedy — `NOT_FOUND`, a discarded direction (`CONFLICT`, CAL-083's no-un-discard doctrine read one step further), a choice made before the analysis is validated (`ANALYSIS_NOT_VALIDATED`), and an unacknowledged change (below). Choosing the one already retained is refused too: the screen is stale, and writing again would move a timestamp that puts the whole downstream chain in doubt |
| obsolescence en aval d'une direction | `CanonicalDirectionObsolescence` in `@calepin/shared/obsolescence` (CAL-086) — `SourceTextObsolescence`'s twin one rung down, over `DIRECTION_DEPENDENT_STAGES` (`bible` / `outline` / `chapters`, computed from the chain, never listed). **Derived, never stored**, and judged against the canonical direction's own `updatedAt`: that column is the only thing that moves when the direction the novel follows moves — becoming canonical, ceasing to be, or being rewritten — so a `canonicalSince` beside it would be a second answer able to disagree with it. Two answers from one read: `current`, what stands in doubt today and clears stage by stage as the author walks back down the chain, and `onChange`, what a change made now would put in doubt — every downstream stage the project holds, because at the instant of a change all of them predate it. **Nothing is deleted and nothing is regenerated**, which is the backlog's requirement for this change in the same words it used of a source-text edit |
| confirmation d'un changement de direction | `SelectCanonicalDirectionInput.acknowledgeObsolescence` — required exactly when the project already holds work built on the direction being replaced, refused otherwise with `OBSOLESCENCE_NOT_ACKNOWLEDGED`. That is what makes _avertir explicitement_ a property of the statement rather than of a screen: a caller that never shows the report cannot get the write through. Not asked on a first choice — nothing downstream descends from a direction that was never retained — and not asked of a project holding nothing below its direction, because a confirmation of an empty warning teaches an author to tick without reading. `OperationEstimate`'s discipline (CAL-057) applied to a decision rather than to a cost |
| direction rédigée par l'utilisateur | `writeUserDirection` in `@calepin/shared/repository` (CAL-085) — a `CreativeDirection` row created with `origin: USER_WRITTEN`, not canonical, not discarded, otherwise identical in shape to a row `propose-directions` would have written. _Alimente la bible aussi bien qu'une direction générée_ is therefore a property of the schema rather than a special case: `getDirectionsForComparison` already reads `origin` without branching on it, and nothing downstream needs to know a row came from a person rather than a model. Under `withProjectTransaction`, not a bare `create` — the row has no existing `CreativeDirection` for a `scopedWhere` to protect, so the project itself is reconfirmed at the transaction's own open, `requireOwnedRow`'s reasoning one level up |
| degré de liberté | `FreedomLevel` = `LOW` / `BALANCED` / `HIGH` — a stored choice in the schema, a **policy** in `@calepin/shared/freedom-level`: one `DimensionTreatment` per `SourceDimension`, and nothing else differs between the three (CAL-044) |
| dimension du texte source | `SourceDimension` — the ten axes a novel can stay faithful to or depart from, drawn from what the analysis produces and what a direction declares |
| traitement d'une dimension | `DimensionTreatment` = `preserve` / `extend` / `reinterpret`, in that order: a level is a **ceiling**, so declaring less than allowed always passes |
| contrainte d'un degré de liberté | `FreedomConstraint` — one clause per dimension plus the stage's own rule, for each of the four `FREEDOM_CONSTRAINED_STAGES`. Declarative French, stated of the novel and never addressed to a model: the _rule_ is the business layer's, the instruction built around it is `@calepin/ai`'s, the same division §5.5 already draws for a mission's schema. The author reads the same sentence the prompt will quote |
| écart au texte source | `sourceDeparture` over a declaration, `sourceDepartureBudget` over a level — the sum of treatment ranks, on one scale, which is what makes "`LOW` closer to the source than `HIGH`" arithmetic. A measure, never the gate: the gate is per-dimension (`checkFreedomCompliance`) |

It deliberately leaves a running attempt alone: the worker holding the call is the only party that can say what the provider was asked for, so it settles its own attempt with the usage it really reported, and closing the attempt from here would either invent a number or throw a real one away. Terminal, and never a failure — `failureClass` and `errorCode` are cleared, so nothing offers _Relancer_ for it. Already cancelled is a success (a second click is the same decision); succeeded or failed is a `CONFLICT`, because the remedy is to look again rather than to try again. A column rather than a message, so a killed worker loses nothing and no pub/sub exists to go wrong; `GENERATION_LEASE_RENEWAL_MS` is therefore the cancellation latency, which is why it is five seconds. `lost` surrenders too — an attempt somebody else reclaimed is one whose answer is already destined for `superseded` |

It also stops the permanent-failure branch overwriting a person's decision with `FAILED`. `runGenerationAttempt` reports it as `{ kind: "skipped", reason: "cancelled" }` — the job did what was asked, so nobody is shown an error for pressing _Annuler_ |
| rejeu d'une génération | `replayGeneration` — reopens a failed generation, never a second row.
